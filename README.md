# Mini NPU Simulator

2차원 숫자 배열로 표현된 패턴과 필터의 MAC 점수를 계산하는 Python 콘솔 프로그램이다.

외부 라이브러리 없이 반복문으로 MAC 연산을 구현하고, 사용자 입력 및 JSON 데이터에 대해 판정과 성능 분석을 수행한다.

## 1. 실행 환경

실행 확인 환경:

- Windows / PowerShell 5.1
- Python 3.15.2
- 외부 패키지 설치 불필요
- 사용한 표준 라이브러리: json, math, re, pathlib, time, csv, platform, statistics, sys
- 테스트 도구: unittest

## 3. 실행 방법

프로젝트 폴더에서 실행한다.

```powershell
python main.py
```

메뉴:

- 1: 사용자 입력 모드
- 2: data.json 분석 모드
- 3: 생성 패턴 분석
- 0: 종료

### 모드별 판정과 집계

| 실행 경로 | 입력 | 판정 | 정답 비교·집계 |
|---|---|---|---|
| 모드 1: 수동 입력 | 3×3 필터 A·B와 패턴 | A / B / 판정 불가 | expected 비교와 PASS/FAIL 집계 없음 |
| 모드 2: JSON 분석 | 원본 JSON의 필터·패턴 | Cross / X / UNDECIDED | expected와 비교해 PASS/FAIL·실패 유형별 집계, 실패 케이스·사유 출력 |
| 모드 3: 생성 패턴 | 홀수 크기와 Cross·X 선택 | Cross / X / UNDECIDED | 생성한 종류와 판정을 함께 표시하며 일괄 PASS/FAIL 집계는 하지 않음 |
| 별도 비교 프로그램 | 생성 X 패턴과 Cross 필터 | 라벨 판정 대신 계산 점수 일치 확인 | 세 측정 경로의 시간과 CSV 출력 |

두 모드는 같은 decide_label()과 EPSILON을 사용하므로 수학적 동점 기준은 같다. 모드 1은 임의로 입력한 두 필터를 A·B로 표시하고, 동점이면 판정 불가로 안내한다. expected가 없으므로 PASS/FAIL을 집계하지 않는다. 모드 2는 표준 라벨 Cross·X로 판정하고 expected와 비교한다. UNDECIDED는 정답 라벨이 아닌 판정 상태이므로 Cross·X 중 하나인 expected와 일치하지 않아 FAIL로 집계한다. 요구사항에 맞춰 출력과 정답 비교를 구분한 것이며, 모드마다 epsilon을 다르게 적용한 것은 아니다.

수동 입력은 [4절](#4-사용자-입력-모드), JSON 규칙은 [5절](#5-json-분석-모드), 실패·복잡도 분석은 [8절](#8-결과-리포트), 생성기는 [14절](#14-보너스-패턴-생성기), 1차원 비교와 라운드별 측정 기록은 [15절](#15-보너스-1차원-배열-mac과-성능-비교)에서 확인할 수 있다.

## 4. 사용자 입력 모드

3×3 필터 A, 필터 B, 패턴을 순서대로 입력한다. 각 배열은 3줄이며 각 줄에 숫자 3개를 공백으로 구분한다.

입력 예:

```text
0 1 0
1 1 1
0 1 0
```

열 개수가 다르거나 숫자로 변환할 수 없는 값이 있으면 오류가 발생한 행만 다시 입력받는다.

nan과 inf 등 유한하지 않은 값도 입력 오류로 처리한다. 재입력 횟수 제한은 없으며, 입력 중 Ctrl+C를 누르면 메뉴 복귀가 아니라 프로그램 전체를 종료한다. 배열 입력 중의 0은 취소 명령이 아니며, 메뉴에서만 0을 종료 선택으로 사용한다.

입력 오류 안내의 형식은 다음과 같다. 아래는 잘못된 행에 대한 메시지 예시이며, 해당 행을 올바르게 다시 입력하면 나머지 입력을 이어간다.

```text
입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.
입력 형식 오류: 숫자로 변환할 수 없는 값이 있습니다.
```

필터 A와 B는 입력으로 지정하는 임의의 필터이다. 계산 후 A/B/판정 불가와 각 필터의 점수를 출력한다.

계산 결과를 출력할 때 두 점수 차이의 절댓값이 1e-09 미만이면 판정 불가라는 기준을 함께 안내한다. 승패가 정해진 경우에도 같은 안내를 표시한다. 이는 기존 EPSILON=1e-9 정책의 설명이며, 점수식이나 동점 경계 조건을 바꾼 것은 아니다.

성능 표는 입력한 패턴과 필터 A에 대한 MAC 호출 시간을 표시한다. 필터 두 개의 전체 판정 시간은 아니다. 시간은 ms 단위의 소수점 여섯 자리로 출력한다. 다음은 2026-11-15 모드 1 실행에서 기록한 평균 0.001947ms를 표 형식으로 옮긴 예시이며, 새로 측정한 값이 아니다.

```text
크기       평균 시간(ms)    MAC 횟수(N²)    반복 횟수
3×3           0.001947               9         1000
```

## 5. JSON 분석 모드

filters에서 size_5, size_13, size_25 필터를 읽는다. JSON 모드의 지원 크기는 5×5·13×13·25×25이다. patterns의 size_N_idx 형식 키에서 N을 추출하여 필터를 선택한다. 3×3 수동 입력과 생성 모드의 크기 정책은 JSON 모드와 별개다.

키의 허용 예시는 size_5_1, size_13_2, size_25_1이다. size_5_bad는 형식 오류이며, size_7_1은 키 형식은 맞지만 지원 크기가 아니므로 해당 케이스를 FAIL 처리한다. 케이스 번호 idx는 1 이상의 정수이며, 크기와 번호에 불필요한 앞자리 0은 허용하지 않는다.

검증 항목:

- 최상위 filters와 patterns의 자료형
- 케이스 키 형식과 지원 크기
- input과 expected의 존재 여부
- 정사각형 배열 여부와 숫자 자료형
- 유한하지 않은 실수 여부
- 키에 명시된 크기와 실제 배열 크기의 일치
- Cross와 X 필터의 존재 및 정규화 후 중복 여부

파일 로드나 최상위 구조 검증이 실패하면 안내 후 메뉴로 돌아간다. 개별 케이스의 데이터 오류 또는 수치 계산 오류는 해당 케이스를 FAIL로 기록하고 나머지 케이스 분석을 계속한다.

예를 들어 JSON의 expected에 circle을 쓰거나 케이스 키를 size_5_bad로 쓰면 다음과 같은 사유를 출력한다. 이는 오류 메시지 형식 예시이며, 원본 data.json을 수정한 기록이 아니다. 수동 입력 모드에는 라벨 문자열을 직접 입력하는 단계가 없다.

```text
사유: 데이터/스키마 오류: 지원하지 않는 라벨입니다: 'circle'
사유: 데이터/스키마 오류: 케이스 키 형식 오류: 'size_5_bad'
```

오류 유형별 진단은 10절의 「6) 실패 원인을 어떻게 분리하는가?」에 정리했다. 원본 데이터의 세 FAIL은 이 예시와 같은 스키마 오류가 아니라 점수 동점에 해당하며, 8절의 판정 표와 독립 십진 연산 검산에서 근거를 확인할 수 있다.

### 실패 유형별 집계

각 분석 결과에 failure_type을 기록하고, summarize_results()가 사유 문자열이 아닌 구조화된 유형으로 집계한다. 기존 점수·판정·PASS/FAIL·실패 사유는 유지한다.

| 분석 결과 | failure_type |
|---|---|
| PASS | None |
| 동점 판정 | tie |
| 판정과 expected 불일치 | prediction_mismatch |
| 데이터/스키마 오류 | data_schema |
| 수치 계산 오류 | numeric |

원본 JSON의 결과 요약은 다음과 같다.

```text
총 테스트: 6개
통과: 3개
실패: 3개

실패 유형별 집계 (동점은 실패에 포함):
- 동점 판정(UNDECIDED): 3개
- 예측 불일치: 0개
- 데이터/스키마 오류: 0개
- 수치 계산 오류: 0개
```

동점은 실패의 하위 유형이므로 실패 수에 다시 더하지 않는다. 전체는 통과와 실패의 합계이며, 실패는 네 실패 유형의 합계와 같다. 기존 실패 케이스 식별자와 사유 목록도 함께 출력한다. 이 통계는 JSON 케이스의 판정 결과이며, unittest 자동 테스트 115개와는 별개다.

## 6. 구현 요약

### 함수별 실행 흐름

| 단계 | 모드 1: 수동 입력 | 모드 2: JSON 분석 |
|---|---|---|
| 입력 확보 | read_matrix()가 필터 A·B와 패턴을 입력받고 parse_row()가 각 행을 검증 | load_data()가 JSON 파일과 최상위 구조를 검증 |
| 케이스 준비 | 입력한 배열을 calculate_score()에 전달 | analyze_data()가 케이스를 순회하고 analyze_case()가 개별 분석 |
| 크기·라벨 처리 | calculate_score()가 패턴·필터 크기와 값을 검증 | parse_case_size()로 N 추출, get_filters()로 size_N 필터 선택·정규화·검증, expected도 normalize_label()로 통일 |
| 점수 계산 | calculate_score() → mac()으로 필터별 점수 계산 | calculate_score() → mac()으로 Cross·X 점수 계산 |
| 판정 | decide_ab()가 decide_label()의 결과를 A·B·UNDECIDED로 변환 | decide_label()의 결과를 expected와 비교하고 실패 유형 기록 |
| 출력·집계 | run_manual_mode()가 점수·판정·성능 표 출력 | run_json_mode()가 케이스 결과·성능 표를 출력하고 summarize_results()로 요약 집계 |

입력과 검증, 계산, 판정, 출력을 구분해 계산 함수만 독립적으로 검사하고 측정할 수 있도록 했다. JSON 분석에서는 개별 케이스 오류를 analyze_data()가 FAIL로 기록하고 다음 케이스를 계속 처리한다. 파일 로드나 최상위 구조 오류는 개별 케이스를 만들 수 없으므로 별도로 안내하고 메뉴로 돌아간다.

### MAC 계산

같은 위치에 있는 패턴 값과 필터 값을 곱하고 모두 더한다.

```text
score = Σ pattern[row][column] × filter[row][column]
```

mac()은 검증된 배열을 받아 계산만 수행한다. calculate_score()는 배열 검증 후 mac()을 호출한다. 누적 변수 score는 0.0에서 시작하는 float이며, 검증 포함 함수는 계산 중 OverflowError를 잡고 계산 후 NaN·무한대 등 유한하지 않은 결과를 검사해 CalculationError로 처리한다. 값을 잘라내거나 점수를 정규화해 오류를 숨기지 않는다. 1차원 경로도 같은 방식으로 수치 오류를 검출한다.

### 라벨 정규화

- +, cross, Cross → Cross
- x, X → X
- 앞뒤 공백 제거 및 영문 대소문자 통일
- 지원하지 않는 라벨은 오류 처리

normalize_label()은 외부 문자열을 Cross·X로 통일하는 함수다. test_main.py의 TestNormalizeLabel에서 +·cross·대소문자 변형, x·X, 앞뒤 공백, circle 등 비지원 문자열과 None·숫자·bool 같은 비문자열을 검사한다.

정규화를 별도 함수로 분리한 이유는 필터 키와 expected에 같은 변환 규칙을 적용하기 위해서다. 변환 코드가 여러 곳에 중복되면 한쪽에서만 별칭이나 공백 처리가 달라질 수 있다. normalize_label()을 재사용하면 비교 기준을 일관되게 유지하고, 표기 규칙을 바꿀 때 변경 지점을 줄이며, 정규화만 독립적으로 테스트할 수 있다. 다만 새로운 분류 종류를 지원하는 작업은 별칭 추가와 다르며, 16절의 필터·판정·출력 확장까지 검토해야 한다.

### 점수 비교 정책

```python
EPSILON = 1e-9
```

두 점수 차이의 절댓값이 EPSILON보다 작으면 UNDECIDED이다. 차이가 정확히 EPSILON과 같으면 동점이 아니다. 동점이 아니면 점수가 더 높은 필터를 선택한다.

UNDECIDED는 정답 라벨이 아닌 판정 상태로 취급한다.

## 10. 과제 목표 6개 해설

### 1) MAC은 무엇이고 AI에서 왜 중요한가?

MAC은 Multiply-Accumulate, 즉 `s = s + x * w`를 반복하는 계산이다. 입력 x와 가중치 w를 곱해 누적합 s에 반영한다. 신경망의 선형 계층과 합성곱 등은 이러한 가중합을 대량으로 수행한다. 이번 구현의 핵심은 다음 한 줄이다.

```python
score += pattern[row][column] * filter_matrix[row][column]
```

MAC은 계산 패턴이며 NPU에만 존재하는 명령이 아니다. Python의 곱셈 뒤 덧셈은 단일 반올림의 하드웨어 FMA와 동일하지 않다. AI 전체가 MAC만으로 구성되는 것도 아니다. 활성화·정규화·softmax 등도 필요하다.

내 말로 설명하기:
> 입력과 가중치의 곱을 계속 더해 하나의 점수를 만드는 것이 MAC이다. 이 단순한 계산을 매우 많이 반복하는 점이 전용 행렬 가속기를 사용하는 이유다.

### 2) 패턴과 필터를 곱하고 더하면 어떻게 점수가 되는가?

수식은 `S(P,F) = Σ_i Σ_j P[i][j] * F[i][j]`이다. 배열을 길이 N²의 벡터로 펼쳤다고 생각하면 두 벡터의 내적이다. 필터 가중치가 큰 위치에 큰 입력이 들어오면 점수 기여가 커진다. 이진 3×3 십자가끼리는 활성 위치 5곳이 겹쳐 5점이고, 십자가와 X는 중심만 겹쳐 1점이다.

이 점수는 확률이나 정규화된 유사도 백분율이 아니다. 필터의 가중치 크기에도 영향을 받는다. 이번 원본 데이터처럼 서로 다른 모양의 필터에서 동점이 날 수도 있다. 동점 처리 때문에 FAIL이 나왔다고 점수식을 임의로 정규화하지 않았다.

내 말로 설명하기:
> 같은 위치끼리 곱한 값을 모두 더한다. 모양뿐 아니라 필터 가중치도 결과를 바꾼다.

### 3) JSON 키·라벨 규칙과 정규화 이유는?

`size_13_2`의 13은 한 변의 길이이고 2는 케이스 식별 번호이다. 키에서 N을 추출해 `filters['size_13']`을 선택한 다음 실제 배열 크기도 검증한다. 키에 13이라고 쓰였다고 실제 데이터도 13×13이라고 믿어서는 안 된다.

- filter의 cross와 expected의 +는 모두 Cross로 변환한다.
- x와 X는 X로 변환한다.
- 앞뒤 공백과 영문 대소문자를 정리한다.
- 알 수 없는 라벨, 정규화 후 중복 필터는 오류로 처리한다.

내 말로 설명하기:
> `cross`, `+`처럼 뜻이 같은 외부 표기를 내부의 한 가지 라벨로 통일해야 문자열 차이로 오판하지 않는다.

### 4) 부동소수점 오차와 epsilon은?

많은 십진 소수는 이진 float로 정확히 표현되지 않는다. 수학적으로 같은 합도 연산 순서와 반올림에 따라 조금 다르게 표현될 수 있다. 실제 데이터의 `size_13_2`는 십진수 기준으로 두 점수가 모두 7.5이지만, float로 곱셈·누적하면 각각 7.499999999999997과 7.5로 계산된다. 이는 `7.5`와 `7.50`처럼 같은 수를 다르게 표기해서 생기는 현상이 아니라, float 곱셈·누적 과정에서 발생한 반올림 오차다. 7.5 자체는 이진 float로 정확히 표현되지만, 0.3 등의 값을 곱하고 누적하는 과정에서는 반올림 오차가 생길 수 있다.

정책은 `abs(a - b) < 1e-9`이면 UNDECIDED이다. 차이가 정확히 1e-9이면 동점이 아니다. epsilon은 산술 정밀도를 높이는 기능이 아니라 판정 정책이다. 모든 데이터 규모에 보편적인 최적 epsilon이 있는 것은 아니다. 이번 과제는 고정 절대오차를 사용하며 상대오차 정책으로 임의 변경하지 않았다. 무한대·NaN은 동점이 아니라 수치 오류로 처리한다. 점수 규모가 크게 달라지는 별도 문제로 확장할 때는 상대오차와 절대오차의 병용을 검토할 수 있지만, 0 근처와 경계값을 포함한 판정 테스트를 다시 해야 한다. 이는 향후 검토 사항이며 현재 epsilon이나 원본 JSON 판정을 바꾼 것은 아니다.

내 말로 설명하기:
> 작은 표현 오차로 승자를 잘못 고르지 않게 허용 범위를 정한다. 이번 세 사례는 정확한 십진 계산부터 동점이므로 오차를 없애도 정답 라벨을 고를 수 없다.

### 5) 크기별 측정과 O(N²)의 근거는?

바깥 반복문 N회와 안쪽 반복문 N회로 모든 원소를 방문한다. 필터 하나는 N² MAC, 두 개는 2N² MAC이다. 상수 계수를 제외하면 시간 복잡도는 O(N²)이다. 한 변 N이 두 배면 원소 수는 네 배이다. 전체 원소 수 M=N²를 기준으로 표현하면 O(M), 즉 원소 수에 선형이다. 이는 지수적 증가가 아닌 이차 증가이다.

곱셈 하나와 덧셈 하나를 별개로 세는 연산량 표기에서는 1 MAC을 2연산으로 센다. 이 프로젝트의 성능 표는 MAC 횟수를 세므로 25×25는 625이며 1250이 아니다. 필터 한 개를 계산할 때의 개념적 연산량을 나누면 다음과 같다. 곱셈과 덧셈을 별개로 세는 표이며, Python 계산이 하드웨어 단일 FMA 명령으로 실행된다는 뜻은 아니다.

| 크기 | MAC 횟수 N² | 곱셈 횟수 | 누적 덧셈 횟수 | 곱셈·덧셈 합계 |
|---|---:|---:|---:|---:|
| 3×3 | 9 | 9 | 9 | 18 |
| 5×5 | 25 | 25 | 25 | 50 |
| 13×13 | 169 | 169 | 169 | 338 |
| 25×25 | 625 | 625 | 625 | 1250 |

필터 두 개를 계산하면 위 횟수는 각각 두 배이며 시간 복잡도는 여전히 O(N²)이다. MAC 함수는 추가 메모리 O(1), 배열 자체 저장은 O(N²)이다. JSON 전체 저장 공간은 모든 필터와 패턴을 합한 크기에 비례한다.

실측은 코드 구조의 복잡도 설명을 뒷받침할 뿐 그 자체가 증명은 아니다. 짧은 함수에서는 타이머, 함수 호출, 인터프리터 및 시스템 부하 영향이 크다. 서로 다른 PC나 다른 시점의 값으로 NPU 성능을 추정할 수 없다.

내 말로 설명하기:
> N×N 크기의 2차원 배열에서 모든 원소를 한 번씩 처리하므로, 한 변의 길이 N에 대한 시간 복잡도는 O(N²)이다. 이론은 반복문으로 설명하고, 실험에서는 I/O를 제외한 반복 평균으로 경향을 확인한다.

### 6) 실패 원인을 어떻게 분리하는가?

| 원인 | 예 | 진단과 대응 |
|---|---|---|
| 데이터/스키마 | 필터 누락, 잘못된 크기·라벨 | 검증 후 케이스 FAIL, 원인 기록 |
| 로직 | 누적합·인덱스 오류 | 작은 손계산 예제로 재현 후 코드 수정 |
| 수치 계산 | 오버플로, NaN | 유한성 검사, 계산 오류 처리 |
| 비교 정책 | 미세한 차이로 승자 선택 | epsilon 경계 테스트 |
| 점수 방식의 한계 | 정확한 동점과 expected 불일치 | 독립 검산 후 UNDECIDED 및 한계 보고 |

자동 테스트 통과는 구현이 지정한 계약을 지킨다는 뜻이지 모든 패턴을 분류한다는 뜻이 아니다. FAIL을 없애기 위해 데이터나 epsilon을 정답에 맞춰 조절하지 않는다.

내 말로 설명하기:
> 실패는 데이터, 계산 코드, 수치, 판정 정책 순서로 분해해서 확인한다. 정상 계산으로도 동점이면 버그를 고칠 문제가 아니라 현재 방식의 한계를 보고할 문제다.

## 15. 보너스: 1차원 배열 MAC과 성능 비교

### 구현과 정확성

`flatten_matrix()`는 정사각형 숫자 배열을 검증하고 행 우선 순서로 길이 N²의 새 리스트를 만든다. `mac_flat()`은 검증된 동일 길이 배열의 곱셈·누적만 수행하며, `calculate_flat_score()`는 입력 검증과 수치 오류 처리를 담당한다.

기존 2차원 구현과 같은 순서로 곱셈·누적을 수행한다. 생성 패턴(3·5·13·25)과 음수·소수 예제, 원본 JSON 6개 케이스에서 점수의 정확한 일치를 검사했다. 원본 JSON의 판정도 유지되며, 기존 3 PASS / 3 FAIL 결과를 바꾸지 않는다. 1차원으로 바꾸는 것은 점수식을 바꾸거나 분류 한계를 해소하는 작업이 아니다.

평탄화 순서·원본과의 독립성·잘못된 입력·길이 불일치·NaN/무한대·오버플로 등을 포함한 신규 테스트 12개가 통과했다. 비교 측정 관련 신규 테스트 8개까지 포함해 전체 100개 테스트가 통과했다. 성능의 우열 자체는 자동 테스트의 합격 조건이 아니다.

측정값은 실행 시점과 시스템 상태에 따라 달라진다. 준비된 배열 재사용의 이득과 매번 변환하는 비용을 구분해서 해석해야 한다. 고정 필터만 미리 평탄화하고 새 입력만 변환하는 경로는 이번 비교에 포함하지 않았다. 성능 차이에는 반복문·인덱싱·호출 구조 차이가 포함되며, 캐시 효과를 직접 측정하거나 원인별 기여를 분리한 실험은 아니다.

## 16. 평가 대비: 확장 설계

이 절은 평가문항의 변경 상황을 현재 코드에 대입한 설계 설명이다. 아래 확장을 구현하거나 1000×1000 성능을 새로 측정한 기록은 아니다. 제출 프로그램의 Cross·X 분류, JSON 지원 크기, epsilon과 기존 판정 결과는 유지한다.

### 새 라벨 o가 추가된다면?

먼저 o가 기존 라벨의 다른 표기인지, 새로운 분류 종류인지 구분한다. 기존 라벨의 별칭이라면 normalize_label()의 변환 규칙과 관련 테스트를 보완하면 된다. 여기서는 o를 별도 분류 Circle로 추가하는 상황을 가정한다. 이 경우 정규화 표에 항목 하나를 추가하는 것만으로는 동작하지 않는다.

현재 get_filters()는 필터 라벨 집합이 Cross·X인지 검사하고, decide_label()은 두 점수만 받는다. analyze_case()와 결과 출력도 Cross 점수·X 점수를 직접 다룬다. 따라서 다음 순서로 확장한다.

1. 표준 라벨 Circle과 허용할 외부 표기를 정의하고 normalize_label()에 반영한다. UNDECIDED는 계속 정답 라벨이 아닌 판정 상태로 구분한다.
2. 각 지원 크기에 Circle 필터를 준비하고, get_filters()의 필수 라벨 집합과 누락·중복 검증을 세 분류에 맞춘다. 기존 원본 데이터는 보존하고 확장용 데이터에서 검증한다.
3. 라벨별 점수를 사전 등으로 저장하고, 두 점수 전용 판정을 여러 점수 중 최댓값을 선택하는 구조로 일반화한다. 각 필터와 패턴의 크기·수치 유효성 검사는 유지한다.
4. 다중 분류의 동점 정책을 명시한다. 예를 들어 상위 두 점수 차이가 기존 EPSILON 미만이면 UNDECIDED로 처리할 수 있다. 이는 확장안이며 현재의 두 점수 비교 정책을 바꾼 것은 아니다. 전부 동점·상위 두 개 동점·epsilon 경계도 검사한다.
5. JSON 결과와 콘솔 출력을 라벨별 점수 순회 방식으로 바꾸고, 정규화된 expected와 비교한다. 실패 유형 집계는 계속 재사용하되 Cross·X 전용 필드에 의존하는 부분을 정리한다. 모드 1의 A·B 입력은 기존 두 필터 비교 기능으로 유지할 수 있다.
6. 정규화, 필터 선택, Circle 승리, 기존 라벨 승리, 동점, 누락 필터, 비지원 라벨, 결과 출력과 집계 순서로 테스트를 추가한다. 원본 JSON 6개 판정과 기존 모드의 회귀 검사도 유지한다.

필터 종류가 C개라면 패턴 하나의 계산량은 C×N² MAC이다. 분류 수가 고정되어 있을 때 N에 대한 시간 복잡도는 여전히 O(N²)이며, 분류 수까지 변수로 보면 O(CN²)로 설명한다.

### 1000×1000 패턴을 처리한다면?

한 배열의 원소는 1,000,000개이며 필터 하나의 점수는 1,000,000 MAC, 두 필터 판정은 2,000,000 MAC이다. 이는 연산 횟수이지 실행 시간의 예측값이 아니다. 현재 기본 성능 측정처럼 필터 하나를 1,000회 반복하면 측정 루프만 10억 MAC이며, 사전 유효성 확인과 준비 실행 비용은 별도다. 작은 입력의 측정값에 단순 비례시켜 실제 소요 시간을 확정하지 않는다.

현재 입력 경로가 N=1000을 그대로 허용하는 것은 아니다. 수동 모드는 3×3이며, JSON 모드는 5·13·25만 지원한다. 생성 모드는 3 이상의 홀수만 허용하므로 짝수 1000은 거부한다. 핵심 MAC 함수가 같은 크기의 정사각형 배열을 계산할 수 있다는 것과, 각 모드가 해당 크기의 입력을 지원한다는 것은 구분한다. 확장하려면 입력 경로와 필터 공급 방식부터 정해야 하며, 짝수 Cross의 중심 행·열 정의도 별도로 결정해야 한다.

| 관점 | 예상되는 부담 | 우선 검토할 대응 |
|---|---|---|
| 계산 시간 | Python 반복문이 모든 원소를 방문하고 필터마다 계산을 반복 | 최소 10회라는 과제 기준을 지키면서 반복 횟수를 조정할 수 있도록 설계하고, 큰 입력의 실행 비용을 안내 |
| 배열 저장 | 패턴·필터의 중첩 리스트, 원소 참조와 숫자 객체 비용 | 입력 크기 상한과 메모리 예산을 정하고 불필요한 복사·보관을 줄임 |
| JSON 로드 | json.load()가 여러 필터·패턴을 포함한 파일 전체를 메모리에 적재 | 예상 파일 크기를 제한하고, 더 큰 데이터는 파일 분할이나 순차 처리 가능한 형식을 별도 설계 |
| 평탄화 | 새 리스트를 만들기 위한 O(N²) 시간과 추가 참조 저장 공간 | 고정 필터는 미리 변환해 재사용하고, 새 입력의 변환 포함 비용까지 비교 |
| 검증 | 같은 필터를 케이스마다 다시 검증하는 비용 | 변경되지 않는 필터를 사전 검증해 재사용하는 구조 검토. 외부 입력 검증 자체는 생략하지 않음 |

메모리를 원소 수×8바이트로 단정하지 않는다. 현재 자료구조는 연속된 64비트 실수 버퍼가 아니라 Python 리스트이며, 실제 사용량은 객체와 참조 공유 여부·실행 환경에 따라 달라진다. 평탄화도 기존 숫자 객체를 모두 복제한다기보다 새 리스트에 참조를 저장하는 작업이므로, 배열 형태와 추가 할당을 구분해 측정해야 한다.

최적화는 먼저 계산과 전체 처리의 시간·메모리를 나눠 측정하고 병목을 확인한 뒤 적용한다. 제출 범위에서는 표준 라이브러리와 직접 반복문 조건을 유지하며, 필터 재사용·반복 검증과 변환 감소를 우선 검토한다. 외부 벡터화 라이브러리나 실제 GPU·NPU 실행은 별도 실험으로 구분한다. 15절의 작은 입력 비교만으로 1000×1000에서도 같은 속도 비율이 나온다고 주장하지 않는다.

### CPU와 NPU 관점에서는 어디가 병목인가?

현재 프로그램의 Python 순차 반복문과 CPU 하드웨어 자체의 능력은 다르다. 현재 측정에는 반복문·인덱싱·숫자 객체 연산 비용이 포함되지만, CPU도 SIMD와 멀티코어 등 병렬 처리 기능을 갖는다. 따라서 CPU는 직렬 처리만 가능하다고 설명하지 않는다.

대규모 MAC은 병렬 계산의 기회가 있지만, 연산기에 데이터를 공급하는 메모리 대역폭과 재사용 정도도 성능을 제한한다. 가속기로 옮기면 입력 준비·변환·전송·실행 요청·동기화 비용을 함께 봐야 한다. 작은 작업에서는 이 비용이 계산 시간 감소보다 클 수 있고, 큰 배치나 여러 필터를 묶은 계산에서는 데이터 재사용과 전용 행렬 연산기를 더 활용할 수 있다.

현재 구현만으로 실제 NPU의 병목이나 가속률을 실측한 것은 아니다. 하드웨어별 실행 방식과 비교 조건은 [11절](#11-심화-학습-ai-발전사와-하드웨어-가속)에서 안내한 기존 심화 문서로 연결하고, 실제 검증에서는 장치 내부 계산 시간과 전송을 포함한 전체 시간을 구분한다.
